# Scope & Guarantees

> Honesty is a feature. This document states limits before capabilities.

## End-to-end-verifiability guarantees

| Guarantee | What it means | Mechanism |
|-----------|---------------|-----------|
| **Cast-as-intended** | The encrypted ballot that leaves the voter's device actually contains the choice the voter made — malware or a malicious casting server cannot silently substitute a different choice. | TARGET MECHANISM (spec): Benaloh cast-or-challenge — the voter may spoil any prepared ballot and audit it on an independent device (the WASM verifier in-browser), plus disjunctive Chaum-Pedersen ZK proofs that each ciphertext is well-formed. CURRENT STATE: NOT implemented in the reference PoC. The PoC's reference/src/election.ts encrypts each vote programmatically (encrypt() + proveBit()) with no challenge/spoil step, no second-device audit, and no voter-facing ballot-preparation UI. The disjunctive Chaum-Pedersen well-formedness proof IS implemented (reference/src/proofs.ts proveBit/verifyBit, 600+ soundness assertions in selftest.ts), but well-formedness alone is NOT cast-as-intended — it proves the ciphertext encodes a legal 0/1 value, not that it encodes the value the human intended. Planned for milestone M3 (cast-or-challenge voter app). HONEST CAVEAT: even fully implemented, cast-as-intended on an untrusted endpoint relies on the voter actually performing challenges on a device not under the same adversary; it is a detection/deterrence property, not endpoint-malware prevention. This is exactly why remote/digital-only profiles cannot claim software independence. |
| **Recorded-as-cast** | The voter's encrypted ballot appears on the public, append-only record exactly as submitted — unaltered, undeleted, unreordered — and the individual voter can confirm their own ballot's inclusion without revealing their choice. | TARGET MECHANISM (spec): a privacy-preserving tracking commitment returned to the voter plus an RFC 6962 Merkle inclusion proof against signed tree heads, revealing nothing about the choice. CURRENT STATE: PARTIALLY implemented. The append-only Merkle bulletin board and its root are real (reference/src/bulletin.ts, RFC-6962-style 0x00/0x01 leaf/node domain separation; canonical serialization in codec.ts). The independent verifier recomputes the root over the published ballots and rejects any tampering (verify.ts check 2; demonstrated catching a flipped ballot in demo.ts attack A). MISSING: no per-voter tracking commitment, no proveInclusion()/audit-proof returned to the individual, no signed tree heads / signing key, no getSignedRoot()/freeze() (the README lists these as the BulletinBoard port interface; the PoC board only exposes append/size/root in-memory). So the PoC proves integrity TO A THIRD-PARTY VERIFIER over the whole set, but does NOT yet give an individual voter the recorded-as-cast confirmation. Signed roots, inclusion proofs, and the Postgres transparency-log adapter are milestone M2; the voter-facing tracker is M3. |
| **Counted-as-recorded** | The announced tally is the honest count of exactly the ballots on the public record — a corrupt authority cannot inflate, deflate, or rig the result without detection. | FULLY demonstrated in the PoC (the strongest guarantee in current code). Additively-homomorphic exponential ElGamal over ristretto255 aggregates the encrypted ballots (elgamal.ts addCiphertexts); only the aggregate is ever decrypted. Each trustee publishes a decryption share with a Chaum-Pedersen proof of correct partial decryption (proofs.ts proveDecryption/verifyDecryption). The independent verifier (verify.ts checks 4-6) re-sums the ballots, re-checks every share proof, recomputes the discrete-log tally, and rejects any claimed tally that does not match the decrypted aggregate (demo.ts attack C: a fake landslide is caught). HONEST CAVEAT: the PoC uses N-of-N threshold decryption (all trustees must contribute; secrets generated independently, never reconstructed), NOT the k-of-n Pedersen DKG the README/spec describes — that is milestone M1/M3 work. N-of-N means any single absent/malicious trustee blocks the count (no fault tolerance). Ranked-choice/write-in via verifiable mixnet (Terelius-Wikstrom) is spec-only, not in the PoC (yes/no contests only). |
| **Ballot secrecy** | No party — including any single insider, trustee, or the casting server — can learn how an individual voter voted from the public record. | DEMONSTRATED for the threshold/aggregate property. The secret key is split across trustees and never reconstructed; each trustee holds only its own share (elgamal.ts). Only the homomorphic aggregate is decrypted, so no individual plaintext ballot is ever recovered. demo.ts step 2 shows a lone trustee cannot decrypt a single ballot. The published transcript contains only ciphertexts + proofs + the aggregate decryption (election.ts Transcript; out/transcript.json carries NO plaintext votes). HONEST CAVEATS: (1) PoC trustees are N-of-N and independently keyed; collusion of ALL trustees would recover individual ballots, and there is no DKG binding them. (2) There is NO anonymity/mixing layer in the PoC and NO identity layer — ballots carry a 'voter-N' label, so unlinkability between identity and ballot is NOT yet provided in code. Belenios-style credentials, decoupled issuance/casting, and the optional Terelius-Wikstrom mixnet are spec-only (M3/M6). (3) Network-level metadata (timing, IP, submission order) is out of scope of the crypto and unaddressed by the PoC. |
| **Receipt-freeness / coercion-resistance** | A voter cannot produce a transferable proof of how they voted, so vote-buying and coercion are defeated by construction; coercion-resistance additionally lets a coerced voter appear to comply while their true vote still counts. | DESIGN PRINCIPLE honored at the protocol level, NOT yet realized as a voter-facing tier. The PoC issues NO receipt at all: the transcript publishes only encrypted ballots and the aggregate result, so there is no 'see your vote' artifact (this is the explicit fix for the original 2014 concept's Step 17 vote-buying receipt; see ADR-8). However, receipt-FREENESS as a usable property requires the recorded-as-cast tracker to be non-transferable (Selene-style fakeable trackers) AND a coercion-resistant casting tier — Selene (deferred fakeable trackers), MACI/Semaphore (zk anti-collusion), or JCJ/Civitas (anonymous credentials, quadratic tally cost, untappable-registration assumption). NONE of these are implemented; all are milestone M6 (optional tiers). HONEST CAVEAT: full coercion-resistance is impossible for remote/unsupervised voting against an adversary physically present at cast time; even the strong tiers carry assumptions (untappable registration channel for JCJ). The platform's stated scope is deliberately LOW-COERCION environments. |

## Deployment profiles

### Profile: `governance (default, low-stakes — DAO / on-chain governance, token/NFT/quadratic/delegated voting, community polls, public-goods/quadratic funding)`

**Use cases.** DAO and protocol governance, token/NFT-weighted votes, quadratic voting and quadratic funding, delegated voting, allowlist (Merkle-root) community polls. Off-chain gasless EIP-712 signed votes (Snapshot-style) with pluggable voting-power strategies frozen at a snapshot block; optional MACI private/anti-collusion tier; optional trustless optimistic settlement (oSnap/SafeSnap) behind a dispute window + timelock.

**Guarantees provided**
- Counted-as-recorded (votes are publicly signed and the tally is independently re-derivable from the published set — the load-bearing property for governance)
- Recorded-as-cast at the set level (append-only board + signed roots; in chain-anchored variants, a ~32-byte signed Merkle root is anchored for tamper-evidence and timestamping — ballots NEVER go on-chain)
- Receipt-freeness ONLY if the optional MACI private tier is enabled; the default open/transparent governance vote is deliberately PUBLIC and is NOT receipt-free

**Guarantees NOT provided**
- Ballot secrecy by default — standard governance votes are intentionally public/attributable for accountability; secrecy/anti-collusion exists only with the MACI tier
- Cast-as-intended against a compromised wallet/endpoint — a malicious wallet can sign a different choice; no Benaloh challenge in this profile
- Coercion-resistance/vote-selling protection in the default tier — public signed votes are inherently a transferable receipt and on-chain stake/token weighting makes vote-markets trivial; only the MACI tier mitigates collusion
- One-person-one-vote — governance is token/stake-weighted by design (plutocratic by construction), which is acceptable for governance but is NOT democratic franchise
- Software independence — fully digital, no paper, no RLA
- STATUS NOTE: governance transport, voting-power strategies, MACI tier, and settlement adapters are milestone M5/M6 — NOT in the current reference PoC.

**Requirements.** A defined membership/voting-power source (token/NFT contract, snapshot block, or allowlist Merkle root); an EIP-712/EIP-1271/ERC-6492 signing path; a bulletin board (object-store or postgres-log); optionally an anchor target (permissioned-BFT or public chain for root timestamping only) and a Safe/Zodiac + timelock for optimistic settlement. Acceptable governance/coordination stakes only; participants understand votes are public unless the MACI tier is configured.

---

### Profile: `society (verifiable internal election — PRIMARY TARGET: clubs, professional/learned societies, associations, HOAs, boards, student government, IACR-style elections)`

**Use cases.** Full end-to-end-verifiable internal secret-ballot elections with a published transcript any member or third party can re-verify, with NO blockchain required. This is the profile the reference PoC most directly prototypes.

**Guarantees provided**
- Counted-as-recorded — fully demonstrated in the PoC (homomorphic ElGamal tally + per-trustee proven decryption + independent verifier; rigged tallies are caught)
- Recorded-as-cast at set level today, with per-voter tracker planned — append-only Merkle board with tamper-detection works in the PoC; voter-facing inclusion proofs/signed roots arrive at M2/M3
- Ballot secrecy via threshold decryption of the aggregate only — demonstrated (no individual plaintext is ever decrypted; a lone trustee cannot unmask a ballot)
- Cast-as-intended once the Benaloh cast-or-challenge voter app (M3) ships — NOT in the PoC yet
- Receipt-freeness as a principle (no transferable 'see your vote' receipt; only ciphertexts + aggregate are published)

**Guarantees NOT provided**
- Eligibility / anti-stuffing by identity — the PoC has NO identity or credential layer and NO nullifiers; it proves ballots are well-formed 0/1 values, NOT that only eligible members voted exactly once. Belenios-style credentials + published nullifiers are milestone M3.
- Unlinkability of identity-to-ballot — no anonymity/mixing layer in the PoC; requires Belenios credentials / decoupled issuance (M3) or the optional mixnet (M6)
- k-of-n fault tolerance — the PoC is N-of-N (one missing trustee blocks the count); k-of-n Pedersen DKG is M1/M3
- Cast-as-intended against compromised endpoints absent the M3 cast-or-challenge app
- Strong coercion-resistance — only the principle holds; Selene/MACI/JCJ tiers are M6, optional
- Ranked-choice / write-in — PoC is yes/no only; mixnet path is M6
- Software independence — no paper, no RLA in this profile by design

**Requirements.** A membership roll or IdP for eligibility (off-ledger; ADR-1: NEVER derive credentials from SSN or durable government ID); k (or N) independent trustees who run the DKG/threshold decryption and never reconstruct the secret; a bulletin board (default postgres-log transparency log with signed roots); the independent verifier run by at least one party other than the operator; voters willing/able to run the cast-or-challenge audit (once M3 ships). Suitable for low-stakes, low-coercion, recoverable elections where a disputed result can be re-run.

### Profile: `polling-place (advanced, software-independent — supervised in-person elections only; opt-in)`

**Use cases.** Everything in 'society' PLUS voter-verified paper ballots of record, mandatory risk-limiting audits (RLA), and endpoint-integrity controls. For supervised, in-person, low-coercion, RECOVERABLE elections that nonetheless want a paper-anchored audit. Explicitly heavy operational burden.

**Guarantees provided**
- All 'society' guarantees PLUS the only software-independence anchor the platform offers: a voter-verified paper ballot is the legal record, inspected before the electronic cast finalizes and retained, with a mandatory RLA where paper WINS on any discrepancy
- Cast-as-intended hardened by paper verification + endpoint controls (reproducible builds, measured boot, chain-of-custody)
- Counted-as-recorded checkable against paper via RLA (an injected endpoint-flip is caught against paper — milestone M4 definition-of-done)

**Guarantees NOT provided**
- Remote/online operation — IN-PERSON, SUPERVISED ONLY; the software-independence guarantee evaporates without physical paper and supervised audit
- Suitability for legally binding government/public elections — see non-goals; this profile is NOT an endorsement for binding public elections, only the most defensible configuration for non-binding supervised use
- Coercion-resistance beyond the supervised polling-place environment itself
- STATUS NOTE: paper VVPAT + RLA tooling is milestone M4 — NOT implemented in the current PoC; this profile is entirely forward-looking.

**Requirements.** Physical polling place with supervised casting; voter-verified paper ballots as the record of truth + secure chain-of-custody; trained election officials; RLA tooling (ballot-polling and/or comparison) and statisticians/observers to run it; endpoint-integrity controls (reproducible/signed builds, measured boot); plus all 'society' requirements (trustees, credentials, board, independent verifier). Highest operational cost of any profile. Use only for NON-binding, recoverable elections.

## Non-goals

- NOT for legally binding government or public elections, in any profile, remote or in-person. This is a firm boundary, NOT a 'fix it later' limitation. It reflects the near-unanimous expert consensus: NASEM 2018 'Securing the Vote'; Park, Specter, Narula & Rivest 2021 'Going from Bad to Worse' (Journal of Cybersecurity); Specter, Koppel & Weitzner 2020 USENIX 'The Ballot is Busted Before the Blockchain' (Voatz analysis).
- NOT a blockchain voting system. The blockchain is explicitly non-load-bearing (ADR-2): it may anchor ONLY signed ~32-byte Merkle roots for tamper-evidence/timestamping; encrypted ballots and proofs NEVER go on-chain. The trust root is peer-reviewed cryptography, not any ledger.
- NOT a defense against compromised voter endpoints in remote/digital-only deployments. Malware can display one choice and record another; an immutable ledger only locks such fraud in. Remote/digital-only profiles state plainly they do NOT achieve software independence (ADR-4). Only voter-verified paper + RLA provides that, and only in the in-person polling-place profile.
- NOT a Proof-of-Stake or stake-weighted authority for franchise elections (ADR-3). Stake is not franchise; PoS as election authority is rejected. Any anchoring chain must be permissioned BFT with named, accountable validators, or a public chain used solely to timestamp roots. (Token/stake weighting is acceptable ONLY in the governance profile, which is explicitly plutocratic-by-design and not a democratic franchise.)
- NOT an identity/eligibility system rooted in SSN or any durable government identifier (ADR-1). Identity proofing stays off-ledger; the voting layer sees only a fresh, unlinkable, per-election 'is-eligible' attestation. No national identity honeypot.
- NOT a 'see your vote on the chain' system. No voter ever receives a transferable proof of how they voted (ADR-8). This deliberately kills the original 2014 concept's Step 17 (a vote-buying/coercion receipt). Verification is via Benaloh challenge + privacy-preserving (Selene-style) trackers, never a public per-voter plaintext.
- NOT a cloud/SaaS product. It is an open, self-hostable, forkable foundation. There is no hosted service that becomes a single point of trust or failure.
- NOT a finished or audited cryptographic system today. The current artifact is a Stage-1 TypeScript reference PoC; the production security-critical path (Rust vvp-crypto -> WASM) and the independent Python verifier, external review, and reproducible signed releases are future milestones (M1, M7). No production security claims until M0/M7 deliverables (signed-off threat model, external crypto review, red-team) are met.
- NOT a coercion-proof system for high-coercion environments. Scope is deliberately LOW-coercion. Even the optional strong tiers (Selene/MACI/JCJ) carry assumptions (e.g. JCJ's untappable registration channel) and cannot defeat an adversary physically present at cast time in unsupervised remote voting.

## Honest-scoping statements (must appear in docs/UX)

- > LOUDEST STATEMENT (must appear at the top of README and SCOPE): 'Do NOT use this for legally binding government or public elections — remote or in-person. This is not a limitation we plan to fix; it is the documented consensus of election-security experts (NASEM 2018; Park-Specter-Narula-Rivest 2021; Specter-Koppel-Weitzner 2020). For binding stakes, the answer is voter-verified paper ballots of record audited by risk-limiting audits (software independence); the digital layer is at most a convenience.'
- > 'The weakest link in any voting system is the voter's ENDPOINT and the COERCION environment, not the ledger. No amount of cryptography or blockchain fixes a compromised device or a coercer in the room. A ledger gives tamper-EVIDENCE for data already recorded; it does nothing for cast-as-intended, ballot secrecy, eligibility, or coercion-resistance.'
- > 'The blockchain here is OPTIONAL and NON-LOAD-BEARING. The default bulletin board is a Postgres transparency log (RFC 6962 signed tree heads) with NO chain. If a chain is used at all, it stores only signed Merkle roots — your encrypted ballots are never written on-chain. If every chain adapter were deleted, every verifiability guarantee would still hold.'
- > 'CURRENT STATE HONESTY: what exists today is a Stage-1 TypeScript reference PoC (reference/), not a production system. It demonstrates exponential ElGamal + disjunctive Chaum-Pedersen ballot-validity proofs + N-of-N (NOT yet k-of-n) threshold decryption with correctness proofs + a Merkle bulletin board + an independent verifier that catches ballot tampering, stuffing-as-invalid-proof, and rigged tallies (2000/2000 randomized soundness tests pass; typecheck clean). It does NOT YET implement: Benaloh cast-or-challenge (cast-as-intended), per-voter inclusion proofs/signed roots (the voter half of recorded-as-cast), any identity/eligibility/credential layer or nullifiers (anti-stuffing today means only well-formedness, not one-eligible-voter-one-vote), any anonymity/mixing layer, paper/RLA, governance transport, or coercion-resistant tiers. Treat unimplemented guarantees as SPEC, not as shipped.'
- > 'NO PRODUCTION SECURITY CLAIMS until M0 (signed-off threat model) and M7 (independent external crypto review + red-team + signed reproducible releases) are complete. The reference PoC is hand-rolled in TypeScript for clarity; the security-critical path is being rebuilt in Rust->WASM with audited crates and cross-checked against the open ElectionGuard verifier and an independent Python verifier written by a different team/language so a single bug cannot mask itself.'
- > 'You never get a receipt that proves how you voted. Verification is designed so anyone can check the ELECTION is correct while NO ONE can prove how any individual voted. This is the explicit reversal of the original concept's see-your-vote-on-the-chain step, which was a built-in vote-buying tool.'
- > 'Profiles are honest about franchise: the governance profile is stake/token-weighted (plutocratic by design) and votes are PUBLIC by default — it is for coordination/governance, not democratic one-person-one-vote secret ballots. The society profile is the secret-ballot E2E-V target. Only the in-person polling-place profile claims software independence, and only via paper + mandatory RLA.'
- > 'Scope is LOW-STAKES, LOW-COERCION, and RECOVERABLE: clubs, societies, associations, HOAs, student/professional bodies, DAOs/governance, community polls and quadratic funding — settings where a disputed result can be re-run. If a vote cannot safely be re-run, or coercion/vote-buying carries real-world leverage over voters, this platform is out of scope.'
- > 'Identity is never rooted in SSN or durable government IDs, and identity proofing stays off-ledger. The voting layer sees only an unlinkable per-election eligibility attestation. We will not build a national identity honeypot.'
