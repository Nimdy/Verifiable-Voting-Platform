# Cryptographic Review — reference proof of concept

> Adversarial audit of `reference/` by independent reviewer lenses. Empirical claims were tested against the running code.

## Verdict

The core ZK/tally machinery is cryptographically sound for its stated stage-1 scope, with one genuine exception in the commitment layer. I independently re-read all of src/ and empirically reproduced the load-bearing claims against the running code (Node 24, @noble/curves 1.9.7). The three Sigma protocols are correctly built and correctly applied: the disjunctive Chaum-Pedersen 0/1 proof and the Chaum-Pedersen decryption-share proof both use strong Fiat-Shamir (the bit challenge binds h, a, and b; the decryption challenge binds G, a, pub, share, plus all commitments), so there is NO frozen-heart / weak-FS hole; the c0+c1==H(...) sub-challenge binding is the real soundness gate and it holds (an m=2 ciphertext cannot be passed off as a bit; cross-key, cross-ciphertext, and cross-trustee replays all fail). Exponential ElGamal, the additive-homomorphic fold, and additive N-of-N decryption are mathematically correct (b - Sigma a^{x_i} = g^{Sigma m}), and serializeBallot is a canonical injective fixed-width 320-byte record. The single thing that breaks the system's own stated property at PoC stage is the bulletin board's Merkle construction: it duplicates the last node on odd levels (the classic CVE-2012-2459 pattern), so [A,B,C] and [A,B,C,C] hash to an identical root (confirmed byte-identical: 570cc377...). That defeats the root's only job — uniquely committing to the ordered ballot multiset — and enables vote injection/deletion against any externally anchored root, which is the explicitly stated production design. Everything else the auditors flagged is either a defense-in-depth nicety or an EXPECTED stage-1 scope gap (no eligibility/nullifier/identity binding, N-of-N instead of k-of-n, no point/scalar validation at a not-yet-existent deserialization boundary). Bottom line: the proof math is right and the tally is honestly verifiable within scope; fix the Merkle malleability before relying on the root, and treat the missing eligibility/identity layer as the non-negotiable prerequisite before any real use.

## Round 10 — verifiable re-encryption mixnet (the primitive for true IRV)

Reviewed the new verifiable re-encryption **shuffle** (`reference/src/mixnet.ts`): `shuffleProve` / `verifyShuffle` / `shuffleChallengeBits`, a **Sako–Kilian cut-and-choose** proof made non-interactive with Fiat–Shamir, operating on items that are ciphertext vectors (Item = `Ciphertext[]`, width W; W=1 degenerate). This is the audit-grade building block true ranked-choice **IRV** needs (shuffle the encrypted ballots, prove the shuffle, then threshold-decrypt the anonymized ballots and run public tabulation).

**Construction chosen for manifest soundness.** A 3-cryptographer design workflow weighed Sako–Kilian against Terelius–Wikström / Bayer–Groth; all three concurred that the O(N) successors are the correct *long-term* construction but the wrong *first* step here, because (a) the non-negotiable is by-hand-checkable soundness, (b) TW/BG need a Pedersen generator CRS with unknown mutual discrete logs that this codebase does not have (it has only single-generator Feldman commitments), and that basis is itself soundness- and privacy-load-bearing, and (c) TW/BG would force extending the audited `hashToScalar` to absorb scalar vectors, whereas cut-and-choose hashes only points and fits the `vvp-fs-v1` frame unchanged. TW/BG are recorded as the documented O(N) efficiency upgrade for a later increment.

**Verdict: sound and private for scope — no soundness/privacy/correctness defect.** Re-encryption-shuffle-equivalence is an equivalence relation (reflexive; symmetric — negate factors mod N; transitive — compose perms, add factors), so for every committed intermediate M_j at most one of the two legs (L0→M_j, M_j→L) is honestly openable; a Fiat–Shamir-bound challenge bit therefore catches a cheat with probability ≥ ½, giving soundness error **2^-t** (t = SECURITY_T = 128 ⇒ 2^-128, 2^128 grinding). Privacy (hiding the permutation π = the voter↔ballot link) is **computational under DDH** + the FS/ROM assumption: exactly one leg is opened per instance, the M_j are never decrypted, and all randomness comes from `randScalar` (never the JS PRNG). The verifier enforces a full-domain bijection on every opened permutation, canonical scalars, the `t ≥ SECURITY_T` floor, an independent FS recomputation that binds pk‖L0‖L‖every M_j, and exact re-encryption equality on **both** components of **all** W components of **all** n items — then always returns a verdict, never throwing.

**Adversarial review (3 lenses — soundness-forgery, privacy-leak, spec-conformance; each finding independently verified): 2 raised, 0 confirmed.** Both were dismissed under verification: an exported-but-dead `applyPerm` (now wired into both prover and verifier so the permutation convention is single-sourced) and an observation that the happy-path selftest sweep is smaller than the spec's aspirational 200 trials (infeasible at t=128 ~2 s/trial; the soundness guarantee comes from the 47-case adversarial tamper battery — section 19, T2–T14 — not happy-path volume). Selftests: ~4,790 trials green including the mixnet block (non-bijection perms, size mismatches, both-component/all-W tampering, plaintext substitution, FS-binding, t-floor, non-canonical scalars, wrong-key re-encryption, never-throws robustness, W=1, domain separation).

**Scope (mirrors ranked.ts):** the sound primitive + independent verifier + adversarial tests ship now. Deferred: the IRV election wiring (shuffle signed ballots off the board → threshold-decrypt the anonymized output → public round-by-round elimination/transfer), the JSON codec + independent Python verifier for shuffle proofs, any UI, and the TW/BG O(N) upgrade.

## Round 9 — ranked transcript JSON + independent Python cross-verifier

Reviewed the new ranked serialization (`rankedTranscriptToJSON`/`rankedTranscriptFromJSON` in `reference/src/transcript-json.ts`), the `kind`-dispatched CLI (`verify-cli.ts`), and a **second, independent** ranked verifier in Python/libsodium (`verifier/vvp-verify-py/vvp_verify.py`), mirroring `verifyRankedTranscript` byte-for-byte.

**Verdict: sound — no soundness bypass, no cross-language divergence.** The wire format publishes the K×K matrix, every bit proof, row/column sum proofs, the credential signature, the Borda aggregates and threshold decryption shares; every group element is validated on parse (`pointFromHex` throws on a bad encoding) and every scalar is range-checked, so a malformed transcript is a clean rejection, never an exception. The transcript carries a `kind:"ranked"` discriminator (version `vvp-ranked-transcript-1`) so a reader dispatches to the correct verifier from the file alone. The Python verifier re-derives the ctx, board root (RFC-6962), signatures, permutation-matrix validity, the homomorphic Borda aggregates, the quorum/share proofs, and the Lagrange-combined tally (bound (K-1)·numVoters; Σ = V·K(K-1)/2) entirely from the public record.

**Cross-language divergence battery (the real bar for a cross-verifier):** ran 13 distinct tampers — padded Borda total, swapped aggregate, mutated matrix ciphertext, swapped bit/row/column-sum proof, non-square (dropped-rank) ballot, extra colSum, double vote, inflated numVoters, forged/swapped signature R, and sub-quorum trustee set — plus the honest control, through **both** the TypeScript CLI and the Python verifier. Result: the honest transcript VERIFIES in both, all 13 tampers are REJECTED by both, and the two implementations agree on every case (zero divergence; identical results `[9,8,7,6]`). CI now produces both `out/transcript.json` and `out/ranked.json`, re-verifies each with the TS CLI from the file alone, and independently re-checks each with Python/libsodium. Added selftest block 18 (ranked JSON round-trip + tamper + bad-encoding-on-parse). Deferred under #49: ranked drill-down UI and true IRV elimination via a verifiable mixnet.

## Round 8 — ranked (Borda) election + verifier

**Verdict: sound and complete — no soundness bypass.** The verifier recomputes the Borda aggregates itself from the published ballots (never trusting prover-supplied aggregates), threshold-decrypts via Lagrange bounded by (K-1)·numVoters, and catches the full attack set (ineligible, double-vote, invalid/non-permutation ballot, tampered ballot/root, wrong aggregate, fake/short shares, sub-quorum, out-of-range index, duplicate roll, numVoters≠ballots, tampered Borda total). ## Round 7 — ranked-choice validity (permutation matrix)

Reviewed the ranked-ballot validity primitive (`reference/src/ranked.ts`): a strict ranking as a K×K permutation matrix of encrypted bits, plus the homomorphic Borda aggregation.

**Verdict: sound for scope — no critical/high defects.** The encoding is provably correct (any 0/1 matrix whose every row and column sums to 1 is a permutation matrix); the proofs are binding (bit proofs force 0/1; the L=1 row/column sum proofs are checked against verifier-reconstructed aggregates; mod-N wraparound is infeasible); `verifyRankingValid` checks shape + every bit + every row/column sum with no gap (empty / ragged / short / duplicate-rank / missing-proof all rejected); and `bordaBallotTotals` is a correct public-weight homomorphic score. No non-permutation matrix passes.

**Applied:** documented that `bordaBallotTotals` assumes a verified ballot and that aggregate scores reach [0,(K-1)·V] (so the deferred threshold Borda tally sizes its decrypt bound by (K-1)·numVoters); relabeled the demo's tamper line for accuracy. Deferred to #49 (next increments): threshold Borda tally, ranked transcript JSON, the Python cross-verifier, and IRV-via-mixnet.

## Round 6 — multi-seat "vote for exactly N" (selectionLimit)

Reviewed the generalization of the exactly-one proof to exactly-L (`proveSumEqual`/`verifySumEqual`) and the `selectionLimit` plumbing across both verifiers.

**Verdict: cryptographically sound and correctly bound — no critical/high defects.** `verifySumEqual` plus the per-candidate bit proofs together force exactly L selections; L is bound into **both** the Fiat-Shamir challenge and the verification target (via L·G), so a proof for L can't be reused for L'; the verifier gates `selectionLimit ∈ [1,K]` and rejects a tampered limit (caught by both the per-ballot proofs and the `Σ = L·numVoters` tally check); and the TypeScript and Python verifiers are **byte-for-byte consistent** on the new `sum-eq` hashing. Plurality (L=1) is preserved exactly via thin aliases.

**Fixed in response:** the Benaloh `auditSelection` was hardcoded to L=1; it's now generalized to multi-pick so multi-seat ballots are also cast-as-intended auditable. (Optional future hardening: bind `selectionLimit` into `electionContext` for signature/root coverage — not required for soundness since the proofs + tally already bind it.)

## Round 5 — hierarchical multi-contest ballots

Reviewed the structured/hierarchical layer (`reference/src/structured.ts`): parent groups, drill-down leaf contests, tags, run/verify.

**Verdict: the per-leaf crypto is sound and cross-contest replay is blocked** (each contest binds its id + candidate names into the Fiat-Shamir/signature context, so a ballot signed for one contest fails verification in another — confirmed). Shared credentials across contests reveal only the expected in-scope participation linkage, no integrity break.

**Fixed in response (verified — 4,742 self-tests incl. composition attacks):**
- **CRITICAL — `verifyStructured` checked transcripts in isolation, not the bundle.** A producer could **omit, duplicate, or relabel/substitute** whole (validly-signed) contests and still get `ok:true` — the hierarchy "glue" was unauthenticated metadata. Now `verifyStructured` authenticates the whole structure: it runs `validateSpec`, requires the results to be a **1:1 cover** of the spec's leaf contests, asserts each result's `id`/`candidates` match **both** the spec leaf and its wrapped transcript, and requires all contests to **share one trustee key + eligible roll**.
- **LOW — `validateSpec` hardening:** a parent must be a group node (not a votable leaf), and a spec must have ≥ 1 leaf contest.

## Round 4 — registrar identity-separation

Reviewed the Belenios-style registrar separation (privacy claim, integrity trust-model, ballot-order linkage).

**Verdict: sound for stage-1 — no real privacy defect.** No single party links identity to vote *content*: the registrar holds identity↔credential privately (never serialized, never used by the verifier), the casting server/public see only credential↔encrypted-ballot, and trustees decrypt only per-candidate totals. Deanonymizing one person's actual choice would require the registrar **and** a ≥k trustee quorum **and** an off-protocol single-ballot decryption (no honest path decrypts an individual ballot).

**Fixed in response (verified — BOTH verifiers updated, cross-checked in CI):**
- **MEDIUM — the verifier trusted attacker-controlled `numVoters`** as the discrete-log bound and the tally-sum target (a denial-of-verification via a huge value, and a merely self-consistent sum check). The shape gate now pins `numVoters === ballots.length` and the discrete-log bound is derived from the real ballot count — in **both** the TypeScript and Python verifiers.
- **LOW — eligible-roll duplicate check** added so a padded roll can't inflate the apparent electorate — in both verifiers.

**Documented as intrinsic / stage-1 (not bugs):** the registrar alone learns per-identity **turnout** (credentialPub is the public eligibility join key); in stage-1 it holds each voter's full signing key, so full "safe if registrar OR server is honest" integrity awaits the voter-contributed credential part (M3+). Hiding turnout needs anonymous/blind-signature issuance (M3+).

## Round 3 — k-of-n threshold key generation & decryption

A third adversarial review covered the threshold scheme (Shamir/Feldman DKG, Lagrange combination, modular inverse) and how the verifier consumes it.

**Verdict:** the threshold core (`threshold.ts`), the modular arithmetic (`group.ts`), and the verifier integration (`verify.ts`) are **cryptographically sound** for scope — validated with 230+ targeted checks plus the self-test. Confirmed: `dkg` produces a correct Shamir+Feldman sharing (publicKey = C₀ = gˣ); verification keys are recomputed from the **public commitments** (no claimed key is ever trusted); Lagrange combination recovers aˣ for **any** quorum of ≥ k and leaks nothing below k; a wrong or forged decryption share is always caught; tampering the commitments is caught; and no wrong tally is ever accepted as valid.

**Fixed in response (verified — 4,704/4,704 self-tests):**
- **Trustee-index range enforcement (LOW).** The transcript now carries `n`, and the verifier rejects any decryption share whose index is not a registered trustee `1..n` — closing a participation-attribution gap where a coalition already holding k shares could mint *phantom-index* shares (it never changed the tally, but could misrepresent who decrypted). (`reference/src/verify.ts`, `election.ts`)
- **`invMod(0)` now throws** instead of silently returning 0. (`reference/src/group.ts`)

Remaining stage-1 gap: the DKG *coefficient sampling* is simulated in one process; a production deployment runs the distributed multi-party DKG so no machine ever sees the secret (the public output is identical, so the verifier is unchanged). → M3.

## Expected stage-1 gaps (fine now, must close before real use)

- No eligibility credential, ballot signature, or one-vote-per-voter nullifier (election.ts BallotEntry.voter is a cosmetic label; verify.ts never checks authenticity/uniqueness/roll size). The whole integrity claim reduces to 'the authority's chosen set of well-formed 0/1 ballots was summed honestly', so anyone who can append to the board can stuff unlimited self-generated valid '1' ballots and the verifier still reports VERIFIED. This is the single largest gap and a non-negotiable prerequisite before real use; fine to omit only because it is explicitly scoped out — but the demo's 'no insider can cheat unseen' framing overstates the current guarantee.
- The ballot validity proof binds no electionId, voterId, or board position (Fiat-Shamir input is only ['ballot-bit', h, a, b, commitments]). A verbatim copy of another voter's (ct, proof) verifies and is counted (copy-cat / Italian attack, demonstrated as tally 4->5 by audit 3), and the same proof replays in any other election sharing the joint key h. Acceptable for an in-process stage-1 demo; must be closed by binding the FS hash to electionId+voterId (and ideally encrypting the contest id inside the ballot, ElectionGuard-style) together with the eligibility/nullifier layer above.
- N-of-N additive trustee key combination instead of k-of-n threshold (elgamal.ts combinePublicKey/decryptionShare). It is correctly labeled N-of-N and confidentiality is fine (the secret is never reconstructed), but there is zero fault tolerance: one offline/obstinate trustee makes the aggregate permanently undecryptable, and a malicious trustee cannot flip the tally (verifyDecryption catches a provably wrong share) but can hold the election hostage by withholding. Replace with a Pedersen-DKG + Shamir k-of-n + Lagrange-combine threshold scheme before production.
- No point subgroup/canonical-encoding validation or scalar range check at a deserialization boundary. This is latent, not exploitable, because codec.ts only serializes — there is no parser, and every Point in the PoC is a trusted in-process @noble object validated on construction; ristretto255 also structurally eliminates small-subgroup/cofactor/non-canonical malleability IF decoding goes through fromHex. The moment real I/O is wired in, every transcript point MUST be decoded via RistrettoPoint.fromHex (wrapped in try/catch so malformed input is a clean verification failure) and every scalar bounded to [0,N); additionally reject the all-zero identity where a non-identity element is required (trustee pubs, arguably ciphertext component a). This is the most likely place a production port silently breaks the discrete-log assumptions the proofs rely on.
- discreteLog uses an O(tally) linear brute-force scan (elgamal.ts:56-63) and the loop bound in verify.ts:77 comes straight from the attacker-influenced t.numVoters; the worst case (no m in range) runs the full max+1 iterations before throwing. Harmless at demo scale but, presented as the production trust anchor, it is an availability/DoS hazard at national scale. Fix with baby-step/giant-step (O(sqrt(max))) and derive the bound from the count of proof-valid ballots rather than the self-declared numVoters field.
- n=1 trustee elections are accepted (setupTrustees/runElection have no minimum), which silently collapses the headline 'no single party can decrypt a ballot' privacy property since one trustee then holds the whole key. Acceptable PoC simplification, but reject n<2 and surface the trustee count in verifyTranscript so the guarantee is not misrepresented.
- 0-voter election verifies cleanly with tally 0 (mathematically correct) but the empty board commits to the fixed constant sha256(''), and with no electorate-size/turnout binding an authority can publish an empty validly-verifying transcript that is indistinguishable from wholesale ballot suppression. Low severity; the real remedy is the eligibility/turnout binding above plus an empty-tree sentinel.
- DecProof needlessly transmits its challenge c and verifyDecryption recomputes-and-compares (proofs.ts:114). Defense holds today, but the transmitted c is dead weight that becomes a trivially-forgeable weak-Fiat-Shamir hole if a future refactor ever drops the equality check; drop c from DecProof and always recompute (mirroring how BitProof omits the bound challenge).

## Next hardening

- Fix the Merkle construction now (RFC-6962 promote-unpaired-node, no self-duplication; optionally bind entry count and add an empty-tree sentinel). This is the only change required to restore a property the PoC already claims to provide.
- Tighten verifyBit to reject non-canonical scalars (raw range check 0 <= c0,c1,s0,s1 < N and unreduced sum compare), matching the stricter style already in verifyDecryption.
- Make hashToScalar (group.ts:53-59) unambiguous and self-describing: length-prefix the label and length-prefix/fixed-count the point list (e.g. sha512(LEN(label)||label||LEN(points)||p0||p1||...)). Domain separation is collision-free today only because the two labels happen to be equal byte length and ristretto points are fixed 32 bytes; any third proof type with a different-length label would open a cross-protocol challenge collision.
- Add a single decode helper pointFromBytes() in group.ts routing every parsed point through RistrettoPoint.fromHex (try/catch -> clean verification failure), bound every scalar to [0,N), and assert non-identity for trustee public keys and any element required to be a real generator-derived key — to be in place before any byte-level transcript deserializer is added.
- Replace the linear discreteLog with baby-step/giant-step (cache the giant-step table across verifications) and derive the search bound from the count of proof-valid ballots, capping it so an attacker cannot inflate the range via a self-declared numVoters.
- Add the eligibility/identity layer: published voter-credential roll, per-ballot signature or membership proof over (ballot bytes || electionId), a deterministic per-voter nullifier checked for global uniqueness, and verifier checks of ballots.length and the nullifier set against the roll (cf. Helios/Belenios/ElectionGuard). Bind proveBit/verifyBit to electionId+voterId so copied/re-randomized ballots cannot be re-attributed.
- Move from N-of-N to a real k-of-n threshold (Pedersen DKG with verifiable shares + complaint/disqualification rounds; Lagrange-combined decryption over the present subset) for liveness and robustness; reject n<2 trustees and surface the trustee count in the meantime.
- Defense-in-depth: drop the transmitted challenge c from DecProof and always recompute it; resample randScalar if it returns 0 (negligible ~2^-253 but removes the HVZK edge case); correct the misleading mul() comment in group.ts:34-37 (@noble rejects the 0 SCALAR, hence the k===0n guard is required, but does NOT reject the identity point in this version, so the P.equals(ZERO) line is defensive/redundant, and mul is intentionally not constant-time which is safe only because all secret scalars are full-entropy).

### Group arithmetic and encodings (group.ts, elgamal.ts): mul() identity/zero-scalar guard, ristretto255 canonical encoding & point validity on deserialization, randScalar sampling bias, exponential-ElGamal correctness / g^m encoding / additive homomorphism / discreteLog brute force, and N-of-N additive trustee key combination vs k-of-n threshold DKG.

_The ElGamal core in elgamal.ts is cryptographically correct: encrypt produces (g^r, g^m·h^r), addCiphertexts is a genuine additive-homomorphic fold, and the additive trustee decryption recovers g^{Σm} exactly. The group.ts primitives are sound: randScalar's 64-byte-reduce-mod-N bias is ~2^-260 (negligible, claim accurate), and mul()'s k===0n guard is genuinely required because @noble's multiply throws on scalar 0 (I confirmed empirically against the pinned 1.7.x). Two of the prompt's hypothesized bugs do NOT hold and I want to be explicit: (1) the mul() identity guard `P.equals(ZERO)` is redundant — @noble does NOT reject identity·scalar in this version (the code comment is wrong about that), but it is harmless; and the constant-time concern is correctly irrelevant because all secret scalars (x_i, r) are full-entropy so the special-case branches are statistically unreachable. (2) ristretto255 structurally eliminates small-subgroup/cofactor/non-canonical-encoding malleability IF decoding goes through fromHex — and in this PoC nothing deserializes attacker bytes at all (all Points are trusted in-process objects), so the validation gap is purely latent. The two findings that genuinely matter for any path to production are both partly acknowledged scope gaps but real limitations: the discreteLog linear brute force is an O(tally) DoS with an attacker-influenced bound (numVoters) hitting every independent verifier — fix with baby-step/giant-step and derive the bound from verified-ballot count, not the self-declared field; and the N-of-N additive key combination has zero fault tolerance — a single offline or obstinate trustee permanently bricks decryption — which needs a real k-of-n Pedersen-DKG + Lagrange-combine threshold scheme. Net: no exploitable soundness bug in the group/ElGamal math as a PoC; the high-severity items are availability/robustness (discreteLog DoS, N-of-N liveness) plus a latent deserialization-validation gap to close the moment real I/O is wired in._

### Protocol-level soundness: replay/malleability, ballot independence, verifier scope, degenerate parameters (0 voters / 1 trustee)

_The cryptographic core (disjunctive Chaum–Pedersen 0/1 proof, Chaum–Pedersen decryption-share proof, exponential ElGamal, RFC-6962-style Merkle board) is correctly constructed: Fiat–Shamir binds the full statement, sub-challenges must sum to the bound challenge, single-bit proof mutations are rejected, out-of-range votes cannot be proven (verified via the self-test and my own checks). The proofs do what they claim about each ballot and each decryption *in isolation*. The soundness gaps are all at the PROTOCOL boundary — what is and isn't bound, and what the verifier refuses to do. The two highest-impact issues are tightly linked and, in my judgment, EXPECTED but must-call-out stage-1 gaps: (1) the ballot validity proof is bound to nothing identity-specific (no electionId, no voterId, no board position), so a verbatim copy of another voter's ballot verifies and is counted — I demonstrated a fully-verifying transcript that double-counts a target's YES (tally 4→5) — and the same proof replays across any election sharing the joint key; and (2) there is no eligibility credential, signature, or nullifier, so the entire integrity claim reduces to 'the authority's chosen set of well-formed ballots was summed honestly,' permitting unlimited stuffing with self-generated valid 0/1 ballots that still verify. These are the canonical missing layers (Helios/Belenios/ElectionGuard solve them with credential signatures + per-election binding + nullifiers); they are acceptable to omit in a stage-1 PoC ONLY if explicitly scoped out, which the code comments hint at ('voter is a label only') but the demo's headline claim ('no insider can cheat unseen') overstates. Two medium issues are latent guarantee-violations the PoC silently allows: n=1 trustees verifies despite collapsing ballot secrecy (no minimum/threshold enforced), and the homomorphic ciphertext's inherent malleability becomes weaponizable precisely because of gap (1). The 0-voter case is mathematically sound but enables turnout-suppression-as-empty-election (low). One info item: the decryption proof needlessly transmits its challenge (defense currently holds, but it is a weak-Fiat–Shamir regression risk). Net: no errors in the proof math itself; the real soundness deficits are missing identity/eligibility binding and degenerate-parameter acceptance, which are the right things to fix before this 'seed' grows into anything deployable._

### codec.ts + bulletin.ts: canonical/injective serialization and Merkle-tree second-preimage / CVE-2012-2459 root ambiguity

_The serialization layer (codec.ts) is sound: serializeBallot is a canonical, injective, fixed-width 320-byte record (10 x 32 bytes; confirmed empirically that every Ristretto point and every scalar is exactly 32 bytes, identity included), so two distinct ballots cannot serialize identically. The leaf/node domain separation in bulletin.ts (0x00 for leaves, 0x01 for internal nodes) is correct and provides genuine second-preimage resistance against leaf/internal-node confusion. However, the Merkle tree's odd-node 'duplicate last' rule (bulletin.ts:43) is the real soundness bug: it is the classic CVE-2012-2459 construction, and I confirmed end-to-end against the actual modules that ballot sets [A,B,C] and [A,B,C,C] produce a byte-identical root (honest transcript root 04d1e6ec... equals the duplicated-set root, and the honest transcript still verifies). The Merkle root therefore does not uniquely commit to the ordered ballot multiset, defeating the stated purpose of the on-chain root anchor and enabling a vote-injection / deletion-ambiguity forgery against any party that pins the root externally. The verifier recomputes the root over exactly the presented ballots, which keeps a single transcript internally self-consistent (the duplicate is counted in the tally too) but cannot detect the malleability against an external anchor. Fix: adopt the strict RFC-6962 promote-unpaired-node rule (no self-duplication) and/or bind the entry count into the root. This is a genuine soundness defect, not a PoC scope gap._
