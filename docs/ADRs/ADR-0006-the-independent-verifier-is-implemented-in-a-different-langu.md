# ADR-0006: The independent verifier is implemented in a different language and by a different team than the core

**Status:** Accepted

## Context
The trustlessness of an E2E-V system rests on independent re-verification of the public transcript: anyone can recheck every claim (key combination, board root, per-ballot validity, homomorphic aggregate, decryption-share correctness, final tally) trusting only the math, as src/verify.ts demonstrates against the transcript produced by src/election.ts. But if the verifier and the prover share the same codebase, language, library stack, and authors, a single shared bug -- a mis-specified Fiat-Shamir hash input, an off-by-one in serialization, a curve/encoding quirk -- can be present in BOTH and thus mask itself: the verifier 'agrees' with a flawed prover. The reference PoC already separates verify.ts from election.ts logically, but both are TypeScript using the same @noble primitives, so they do not yet provide language/team independence.

## Decision
The security-critical core (proving, encryption, DKG, tally) is implemented in Rust (vvp-crypto, compiled to WASM) using audited crates (curve25519-dalek, Merlin/STROBE for Fiat-Shamir). The INDEPENDENT VERIFIER is implemented in a DIFFERENT language (Python, verifier/vvp-verify-py) by a DIFFERENT track/team, sharing no code with the core and reading only the canonical published transcript. A transcript is considered verified only when it passes under MULTIPLE independent implementations: the Rust core's own checker, the Python reference verifier, AND the open ElectionGuard verifier (M1 definition-of-done). The transcript format (vvp-transcript) is a language-neutral canonical encoding (protobuf/JSON) precisely so independent reimplementations can consume it. Domain-separation labels, hash inputs, and serialization are pinned in CRYPTO_SPEC.md as the contract both sides implement against, so divergence surfaces as a verification failure rather than hiding.

## Consequences
GOOD: a single implementation bug cannot silently validate a bad transcript -- it must occur identically in two unrelated stacks and an external third (ElectionGuard) to go undetected, which is enormously less likely; interoperability with ElectionGuard's verifier gives an external, widely-reviewed cross-check; forces a clean, language-neutral, fully-specified transcript format (good for third-party auditors and forkers); embodies 'no insider can cheat without being caught' at the software-defect level, not just the protocol level. BAD/COSTS: two-plus implementations of the same crypto must be built and kept in lockstep with the spec, roughly doubling verifier maintenance and creating a synchronization burden when the protocol evolves; cross-language crypto interop is finicky (canonical point/scalar encoding, hash transcript byte-exactness, ristretto255 representation) and demands a shared, frozen test-vector suite; ElectionGuard interop constrains some design choices to remain compatible. These costs are accepted as the price of defense-in-depth against correlated implementation bugs in a system whose entire value is being independently checkable.

## Alternatives considered
(1) Single-codebase verifier (a flag/mode of the prover) -- rejected: shared bugs self-mask; not credibly 'independent'. (2) Same language, different author -- weaker: shared library/encoding bugs (e.g., in @noble or dalek) still correlate; language diversity additionally breaks shared-toolchain bugs, so the stronger bar is chosen. (3) Formal verification of one implementation instead of N implementations -- valuable but complementary and far higher effort; multi-implementation cross-checking gives most of the assurance now and is a milestone gate, while formal methods remain a future enhancement. (4) Rely solely on ElectionGuard's verifier -- rejected: creates a single external dependency and does not exercise our own transcript independently; we require our Python verifier AND ElectionGuard, not either alone.
