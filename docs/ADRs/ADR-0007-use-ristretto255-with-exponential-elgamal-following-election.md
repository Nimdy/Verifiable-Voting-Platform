# ADR-0007: Use ristretto255 with exponential ElGamal following ElectionGuard 2.x; no hand-rolled ciphers

**Status:** Accepted

## Context
The original concept invented 'Scrambled Prime Key Encryption (SPKE)' -- an undefined, security-by-obscurity primitive with no proof, no peer review, and reversible-by-construction properties. A voting system's confidentiality and verifiability must rest on standard, peer-reviewed cryptography. The required properties are: additively homomorphic encryption (to sum encrypted ballots and decrypt only the total), efficient zero-knowledge proofs of ballot well-formedness, threshold decryption with correctness proofs, and a discrete-log setting that is fast, constant-time, and free of the cofactor/encoding pitfalls of raw curve points. The reference implementation already realizes exactly this: exponential ElGamal over ristretto255 (src/elgamal.ts, src/group.ts) with disjunctive Chaum-Pedersen 0/1 proofs and Chaum-Pedersen decryption-correctness proofs (src/proofs.ts), Fiat-Shamir over a domain-separated hash, built on audited @noble/curves primitives -- the same construction family as Helios and Microsoft's ElectionGuard.

## Decision
The cryptographic stack is exponential ElGamal over the ristretto255 prime-order group, following ElectionGuard 2.x semantics and conventions, with: disjunctive Chaum-Pedersen NIZKs for ballot validity (each ciphertext encrypts 0 or 1; per-contest sums well-formed) and Chaum-Pedersen proofs of correct partial decryption; Fiat-Shamir non-interactivity over a Merlin/STROBE transcript that binds the FULL statement (not just commitments) to avoid weak-Fiat-Shamir attacks; Pedersen DKG k-of-n threshold trustee keys where the secret key is NEVER reconstructed (Lagrange-combined partial decryptions only). NO hand-rolled ciphers, curves, or proof systems are permitted. The security-critical path uses audited crates only (curve25519-dalek for ristretto255; the reference PoC uses @noble/curves of the same family). ristretto255 is chosen specifically because it is a prime-order group abstraction over Curve25519 that eliminates cofactor and non-canonical-encoding bugs, giving safe, constant-time, fast operations. ElectionGuard 2.x conformance is enforced via shared test vectors and the requirement (ADR-0006) that transcripts verify under the ElectionGuard verifier.

## Consequences
GOOD: every primitive is peer-reviewed and battle-tested; additive homomorphism means only the aggregate is ever decrypted, so no individual ballot is exposed (src/elgamal.ts, single-trustee-attempt demonstrably fails); ristretto255 removes a whole class of cofactor/encoding vulnerabilities and is fast enough for in-browser WASM; ElectionGuard 2.x alignment grants interoperability with an external, well-reviewed verifier and a documented spec to build against; the disjunctive Chaum-Pedersen proof makes ballot-stuffing (a vote of '2' or '1000') unprovable and therefore rejected. BAD/COSTS: exponential ElGamal requires a discrete-log step to read the tally (brute force over [0, numVoters] in src/elgamal.ts discreteLog), which is fine for vote counts but bounds plaintext magnitudes and needs care for large tallies (baby-step/giant-step or range partitioning); ristretto255 (a 252-bit-order group) is not directly compatible with EVM-native curves, so any on-chain interaction needs adapters (acceptable since the chain is non-load-bearing, ADR-0002); committing to ElectionGuard 2.x conventions constrains future primitive swaps and ties us to that spec's evolution; homomorphic tally alone does not handle ranked/write-in ballots, which require the optional verifiable mixnet (Terelius-Wikstrom). These are accepted as standard, well-understood trade-offs of a proven construction.

## Alternatives considered
(1) Invented/obfuscated cipher (SPKE) -- rejected outright: unproven, reversible, security-by-obscurity. (2) Paillier additively-homomorphic encryption -- rejected as default: larger ciphertexts/keys, slower in-browser, and diverges from ElectionGuard interop; ristretto255 ElGamal is faster and the interop is valuable. (3) Raw Curve25519/ed25519 points without ristretto -- rejected: cofactor and non-canonical-encoding footguns that ristretto255 was designed to remove. (4) BLS12-381 / pairing-friendly curves -- unnecessary for ElGamal+Chaum-Pedersen and heavier; relevant only inside optional zk-SNARK tiers (Semaphore/MACI), kept isolated in circuits/. (5) Lattice/PQ encryption -- premature: immature for verifiable-voting tooling and no ElectionGuard interop; revisitable later as a pluggable TallyingScheme.
