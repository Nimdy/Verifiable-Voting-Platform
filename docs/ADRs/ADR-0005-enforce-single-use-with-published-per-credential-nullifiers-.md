# ADR-0005: Enforce single-use with published per-credential nullifiers, not a time-to-live (TTL)

**Status:** Accepted

## Context
The 2014 concept prevented token reuse with a TTL ('prevents the AAVET from being used again after a certain period', Steps 73, 122). A TTL bounds WHEN a credential is valid, not HOW MANY TIMES it is used: within the live window a credential can be replayed, and clock skew / window boundaries create ambiguous race conditions. The real requirement is exactly-once casting per eligible credential, publicly and verifiably, without revealing who voted for what. The reference design already issues per-election Belenios-style credentials (ADR-0001) and publishes encrypted ballots to an append-only Merkle board (src/bulletin.ts); a nullifier set fits this model cleanly and is publicly auditable, whereas a TTL is an opaque server-side timer.

## Decision
Single-use is enforced by PUBLISHED NULLIFIERS, not TTL. Each credential deterministically derives exactly one nullifier (e.g., a domain-separated value bound to the election identifier and the credential, derived so that one credential yields one and only one nullifier and the nullifier reveals nothing about the credential's owner or vote). On cast, the nullifier is published to the bulletin board / a public spent-set; the casting service and any independent verifier REJECT a second ballot carrying an already-published nullifier. The spent-nullifier set is part of the public transcript, so anyone can confirm (a) no nullifier appears twice (no double-voting) and (b) every counted ballot carries a valid, unique nullifier (no stuffing), without learning voter identities. For the zk tiers (Semaphore/MACI/JCJ) this is the standard nullifier-hash mechanism; for the default Belenios tier it is a one-per-credential tag checked against the published set. Replay protection is thus a public set-membership property, not a wall-clock condition.

## Consequences
GOOD: provides true exactly-once semantics independent of clocks and windows; the no-double-vote and no-stuffing properties become publicly verifiable from the transcript (consistent with 'verify everything'); eliminates TTL race conditions and the in-window replay hole; composes naturally with the existing Merkle board and with zk anti-collusion tiers; a corrupt server cannot silently accept a double-vote because the duplicate nullifier is visible to every verifier. BAD/COSTS: the spent-nullifier set grows monotonically and must be stored and published for the life of the election (modest, one entry per voter, but it is state that must be replicated and made available); nullifier derivation must be specified carefully so it is deterministic-per-credential yet unlinkable and non-forgeable -- a subtle crypto detail that goes in CRYPTO_SPEC.md and must be cross-checked by the independent verifier; revocation/re-issuance of a credential mid-election needs an explicit policy so a reissued credential does not create a second usable nullifier. These are accepted as the cost of public, clock-free exactly-once enforcement.

## Alternatives considered
(1) TTL on credentials (original) -- rejected: bounds time not count; in-window replay and boundary races. (2) Stateful per-voter 'has voted' flag in a private database -- rejected: not publicly verifiable, so a corrupt insider can flip flags or accept extra ballots undetectably, defeating the anti-stuffing guarantee. (3) Blind-signature single-use tokens -- rejected for the default tier per the Belenios choice (ordinary signatures, integrity if registrar OR server honest); blind signatures add a trusted signer and complexity without improving the public-verifiability of single-use. (4) On-chain nonce/replay protection -- rejected as load-bearing per ADR-0002 (chain non-load-bearing); the nullifier set lives on the bulletin board, which may be optionally anchored but is not chain-dependent.
