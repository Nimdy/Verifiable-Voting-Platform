# ADR-0003: No Proof-of-Stake as election authority; permissioned BFT with named validators if any chain is used

**Status:** Accepted

## Context
The 2014 concept specified Proof-of-Stake (PoS) as the consensus algorithm for the voting ledger. Stake is capital, not franchise. Using stake to decide election state is plutocratic capture: whoever holds the most tokens controls ordering, inclusion, and effectively the authority over the record -- the opposite of one-person-one-vote and exactly an insider/whale foothold the project exists to remove. PoS also offers only probabilistic finality (chains can reorg), which directly contradicts the 'immutable, settled record' an election needs. This decision only bites when an operator opts into the anchoring tier from ADR-0002; the default Postgres transparency log uses no consensus at all.

## Decision
PoS-as-election-authority is REJECTED by design. No anchoring chain may serve as the franchise or election authority, and no economic-stake mechanism may decide inclusion/ordering/finality of election artifacts. If an operator anchors (ADR-0002), the only acceptable chains are: (a) a PERMISSIONED BFT chain with a NAMED, accountable validator set (e.g., CometBFT/Cosmos SDK with a published, identity-bound validator roster and instant finality), governed per-jurisdiction/per-org with optional sharding; or (b) a public chain used STRICTLY to timestamp signed Merkle roots, where the chain provides ordering/witness only and contributes nothing to franchise or tally authority. Validator identity, accountability, and the finality model MUST be documented in the ElectionManifest and THREAT_MODEL.md. Because the chain is non-load-bearing (ADR-0002), even a fully compromised validator set cannot alter a tally -- the worst it can do is censor or equivocate on root publication, which the independent verifier and multi-witness anchoring expose.

## Consequences
GOOD: removes plutocratic capture and the whale/stake insider foothold; replaces probabilistic finality with instant BFT finality matching the 'settled record' requirement; named validators are accountable and auditable (you know exactly who could have misbehaved), fitting the 'no anonymous insider can cheat without being caught' mission; permissioned BFT is operationally cheaper and faster than PoS for the small-to-medium scopes targeted. BAD/COSTS: a permissioned validator set is more centralized/trust-scoped than a large public PoS network and must be chosen and justified by the operator (named-validator governance becomes a documented trust assumption); rules out 'just deploy on a public PoS L1 as the authority' convenience; requires per-deployment validator-set governance and key-management discipline. Mitigated by ADR-0002: since the chain is non-load-bearing, the security cost of a smaller validator set is bounded to availability/timestamping, not integrity of the count.

## Alternatives considered
(1) Public PoS L1 as the authority -- rejected: plutocracy + probabilistic finality. (2) Proof-of-Work anchor -- could timestamp roots, but as an AUTHORITY it has the same franchise-mismatch and energy/finality issues; acceptable only in the narrow 'timestamp-only' role (e.g., Bitcoin OP_RETURN anchor) which is already permitted under ADR-0002, not as authority. (3) Permissionless DPoS/delegated stake -- rejected: same capital-as-franchise problem with extra cartel risk. (4) No chain at all (default log) -- the baseline; this ADR governs only the opt-in anchoring case and constrains it to permissioned-BFT-or-timestamp-only.
